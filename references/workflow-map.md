# 动态微信表情：流程总览

本页只回答“从输入到可交付 ZIP 怎么走”。细节见[整套执行](full-album-workflow.md)、[Images 2.6 直出](direct-gif-workflow.md)、[视频账号与费用](video-connections.md)、[输出与边缘质量](output-contract.md)。

| 用户任务 | 首选路线 | 交付边界 |
|---|---|---|
| 做一套，8–24 张 | `album_workflow.py` 计划，Images 2.6 逐张直出 GIF | 同一主体锚图；直出不合适或未过关的编号才走独立视频回退；全部最终 GIF 合格后打包。 |
| 明确试做 1–7 张 | 独立直出 GIF 样片 | 按指定数量验收，不自动升级为整套，不调用整套 `pack`。 |
| 给现成 GIF、静图、九宫格或视频 | 相应的仅后处理或旧网格入口 | 按真实输入处理；现成视频不需要重新生成 GIF 源素材。 |

## 新生成主线

1. **记录需求与费用。** 记录主体、风格、动作、数量和最终 `opaque` / `transparent` 背景模式；不添加未经要求的画面文字。先核对当前模型权限、额度与费用，不能把账号登录视为生成权限。
2. **确认唯一主体锚图。** 新任务只先生成一张，展示并等待用户明确确认，保存锚图哈希与批准记录。确认前不生成动作 GIF、静帧或视频。整套运行 `album_workflow.py plan`，默认 8 张，计划记录直出调用数和按需视频回退上限。
3. **优先直出 GIF。** 核实工具有明确 Images 2.6 模型 ID、GIF 输出与原始文件保存能力；否则检查已配置的 Image API。以已确认主体特征、单一动作和简洁背景写提示词。背景保持静止，不自行添加车辆、路人或持续移动的杂物；首尾姿势和场景状态要接近。逐张调用一次，保存原 GIF、模型/费用收据和哈希。
4. **本地缩放与审片。** 用 `direct_gif_to_sticker.py` 复制或缩为 240×240、≤500000 字节。检查真实多帧、无限循环、背景模式、角色身份、动作和首尾画面；机器可检查文件规格，视觉接缝仍须人工看最终 GIF。只有真透明直出并通过逐帧检查才可用于 `transparent` 模式。
5. **按编号回退视频。** 直出能力不可用、角色漂移、循环失败、动作复杂或透明度不合格时，只对受影响编号制作独立静帧并走现有视频路线。新的付费调用、换模型或重试先复核费用。外部视频批次才使用 `album_workflow.py preflight/authorize-batch/run`；原生视频工具按单张登记。视频转 GIF 后过同一最终验收。
6. **附加素材与打包。** 全部 GIF 达标后制作详情页横幅、透明封面、透明聊天图标及默认成对赞赏图。`album_assets.py` 验证后，以 `album_workflow.py pack` 打包同背景模式的最终 GIF；来源可混合，但逐张保留证据。主体一致性、画面质量及微信平台审核仍需另行确认。

“一键”表示主体图确认后，在已核对费用与授权范围内连续执行；不跳过确认、费用或最终人工审片。已有 Grok → 视频 → GIF 样片证据不能算作 Images 2.6 整套端到端验证，新路线需逐张保留真实结果。
